# Repository audit — 2026-10-13

Scope: (a) raw efficiency, (b) CI coverage for MATLAB↔Julia parity and physical soundness,
(c) UX for non-coders, (d) organization/browsability on GitHub.

Method: read every file in `julia/src`, the tests, the CI workflows, and the core MATLAB
solver. Ran the Julia test suite locally (Julia 1.10.5, 4 vCPU, 15 GB RAM), and ran three
small benchmarks. The scripts are in this folder: `fused_dtn.jl` and `precond.jl`. MATLAB
was not available, so the MATLAB-side findings come from reading the code only.

## TL;DR

- **Tests pass:** 177/177 in 11 m 38 s on 2 threads (measured).
- **The latest cluster sweep passes the experimental-validation gate.** Run
  `output/4193275_*` has amplitude RMSE 0.085 and phase RMSE 6.0°, and all 30 cases
  converged in 11–15 periods. Cases took 116–203 s each.
- **Biggest weakness: the DTN generator.** It allocates
  temporary matrices of roughly `π·nr²·refp²` floats per row. Measured: nr=100 → 75 GB
  total allocated, 32 s; nr=200 → 602 GB total allocated, 498 s. These are totals over
  the run, not resident memory; peak RSS was about 5.7 GB. Both time and allocation grow
  about 8× each time nr doubles, i.e. as nr³. A fused, allocation-free kernel (same math)
  matches the shipped one to 3.6e-16, runs 10× faster at nr=100 and 20× faster at nr=200,
  and allocates 42× less.
- **Biggest solver opportunity:** use one LU factorization (taken at `g_prefactor=1`) as
  a preconditioner for GMRES. Measured at nr=150 over 9 (Γ, f) cases, GMRES then converges
  in **3–5 iterations** with a relative error of at most 1.8e-12 against a direct solve.
  This could replace the 60-entry LU cache (12 GB per case at nr=2500) with one factor
  (200 MB). The plain GMRES fallback needs n iterations (measured: 202/202 and 402/402),
  so it is no better than a dense direct solve.
- **Parity CI is thin.** It covers one bath-driven case, the LU path only, early-stop off,
  at 1e-3 relative tolerance. There is no refinement-convergence test and no analytic-limit
  test.
- **Docs and layout:** the root README links to three sections that commit 4a29df2
  deleted. Several source docstrings still say the code "has NOT been executed". The
  repository tracks 76 cluster-output files, 3 `__MACOSX` files, personal email-helper
  scripts, and figure scripts from another project.

**Single recommendation:** first, swap in the fused DTN kernel and the
LU-preconditioned GMRES step solver, guarded by the existing golden/agreement tests. Then
add a refinement-convergence and quasi-static-limit test tier.

## Action plan (critical path: 1 → 2 → 3)

1. **Fused DTN kernel.** Replace `far_part!` in `julia/src/dtn/dtn_generator.jl` with the
   scalar loop in `docs/audit/fused_dtn.jl`. Do the same for the near-field broadcasts.
   The existing `test_dtn_golden_small.jl` guards correctness. This also shortens CI,
   which spends a large share of its time in `generate_dtn(150, 60)`.
2. **Preconditioned step solver.** Add a `:pgmres` solver: one `lu(Mat(g=1))`, then
   `Krylov.gmres(Mat(g), b; N=F, ldiv=true, memory≈20)`. Make it the `:auto` default when
   the full LU cache does not fit. The existing LU-vs-GMRES agreement test guards
   correctness. Before switching the default, check the iteration count at nr=2500 (one
   case on the cluster).
3. **Measure, then decide on the LU cache.** Time one nr=2500 case with `:lu` and with
   `:pgmres`. Back-of-envelope (see ledger): about 5× fewer FLOPs and 60× less memory per
   case, which lets about 15 cases run at once instead of 4 on a 64 GB node.
4. **Cheap wins.**
   - Deduplicate the LU cache by the cycle's symmetry. Floating-point rounding currently
     defeats the `by_value` dedup: 33–49 unique `g` values out of 60 versus 31 at 12
     significant digits. Fixing it halves factorizations and memory on the `:lu` path.
   - Set `BLAS.set_num_threads(cpus ÷ concurrency)` in `run_sweep`. Today nothing sets
     it, so every concurrent case's LU uses all BLAS threads.
   - Patch `materialize!` in place instead of copying the full n² matrix every step on
     the GMRES path.
5. **Physics CI tier** (fast, small domain):
   - A refinement test: response amplitude and phase change by less than X% between
     nr and 2·nr, and between temporalResolution 30 and 60.
   - A quasi-static limit: at low f, amplitude ratio → 1 and phase lag → 0.
   - Static equilibrium against a hand-computed Archimedes + capillary balance.
   - A domain-size independence test: `bathDiameter` 60 vs 120.
6. **Broader parity.** Extend `JuliaParityTest.m` to a 3×3 grid of cases that adds a
   disk-forced case, an `earlyStop=true` case and a GMRES case. Tighten the tolerance to
   about 1e-8: it is the same algorithm in double precision, so 1e-3 hides real drift.
   Also add a CSV-schema parity check between `sweeper.m` and `run_sweep.jl` output.
7. **Experimental regression in CI.** Run the validation overlay on the committed
   `output/4193275_*` CSVs. This needs no simulation, takes seconds, and catches overlay or
   fit regressions that today only the hours-long slow tier would catch.
8. **README for experimentalists.** Add a top section titled "I just want to run a
   sweep". It should give 3 commands, where output lands, and how to read
   `val_amp_*.png`. Fix the three dead links. Move the API tables lower.
9. **Repository cleanup.**
   - Move `output/` to a Release asset or Git LFS, and actually gitignore it.
   - Delete `__MACOSX/`, `matlab/1_code/*.log`, `sending_email.py` (it contains personal
     addresses) and `certificate_install.py`.
   - Move `Figures/{impact_panel,video_maker,OnePixel,schematics}.m` out: they point to
     another project's `ImpDef...` folders with Windows paths.
10. **Stale comments.** Delete the "written blind / NOT been executed" CAVEAT blocks in
    `gmres_solver.jl` and `dtn_registry.jl`, since CI executes both now. In
    `run_baseline_sweep.sh`, the comment says "16 cores / 32GB" but the header says 4 CPUs
    and 64G; make them agree.

## (a) Efficiency — details

| Measurement (this machine) | Value |
|---|---|
| `generate_dtn(100, 40)` shipped | 32.1 s, 75 GB allocated |
| `generate_dtn(200, 80)` shipped | 498 s, 602 GB allocated |
| `generate_dtn(50, 20)` shipped vs fused | 1.97 s / 9.24 GB vs 0.445 s / 0.22 GB, max rel diff 3.6e-16 |
| fused nr=100 / nr=200 | 3.1 s / 24.5 s |
| per-step cost nr=200, LU cached | 0.6 ms/step; 1 LU = 6 ms |
| plain GMRES iterations, n=202 / 402 | 202 / 402 (= n, no Krylov benefit) |
| LU(g=1)-preconditioned GMRES, nr=150 | 3–5 iterations, err ≤ 1.8e-12 |

Why the DTN generator is slow: `far_part!` builds about 13 dense broadcast temporaries of
size `length(i_far) × length(l_vals)` for every row. That is about
`2·nr·refp × π·nr·refp` elements. At nr=2500 that comes to roughly 3.9e9 elements, or
**about 31 GB per temporary per row**. Native nr=2500 generation is therefore
infeasible as written. The docstring's claim that dropping MATLAB's 20-batch chunking is
"structurally identical" holds for the numbers it produces, but not for memory use.
Extrapolating the fused kernel by nr³ from nr=200 gives about 13 h on 4 threads for
nr=2500 (unverified extrapolation).

MATLAB-side observation (from reading the code): `solve_motion.m` defaults
`debug_flag=true`, so a bare call plots with `drawnow` on every step. Default it to
`false`.

## (b) CI coverage — details

What exists, and it is good: DTN golden test (nr=50 against the MATLAB cache), LU-cache
hit rate, LU-vs-GMRES agreement, 17 physics-grounded checks, and a live MATLAB↔Julia
parity check.

Gaps:
- No discretization-convergence test. The production domain (nr=2500, D=100) is never
  related to the CI domain (nr=150, D=60).
- No analytic limits (quasi-static, Archimedes).
- Parity covers 1 case, 1 solver path, no early stop, at 1e-3 tolerance.
- The DTN parity at nr=2500 (the `D25Quant200` filename mismatch) is still open.
- The MATLAB physics test 16 compares only 2 frequencies; the Julia version checks
  monotonicity over the range.
- Validation against experiment runs only in the slow tier.

## (c) UX — details

- The first screen of the root README is model description plus API tables. An
  experimentalist needs: install, run sweep, where the plots are, what "pass" means.
- `run_sweep_case` silently overrides `fixed.simulationTime` with `30/freqHz`
  (`julia/src/sweep.jl`). A user who edits `simulationTime` in the sweep spec sees no
  effect. Either document it in `SweepSpec`, or make it a field such as
  `maxPeriods = 30`.
- The sweep grid is edited inside code (`default_sweep_spec()` / the top of `sweeper.m`).
  A `sweep.toml` read by `run_sweep.jl` would let non-coders change Γ/f without touching
  Julia.
- `spatialResolution` is described as "intervals per disk radius" in `sweeper.m` and as
  "radial mesh points per disk radius" in Julia. Pick one.

## (d) Organization — details

- The Julia package layout is clean and the module↔MATLAB table is excellent.
  `matlab/1_code` mixes the solver driver, plotting, Python helpers, logs and DTN caches
  (47 MB `.mat` in git).
- Suggested top level: `julia/`, `matlab/`, `data/` (experimental CSVs, DTN caches via
  LFS), `docs/`, with results kept out of git.
- Long "incident history" docstrings (e.g. the 50-line STATUS in `dtn_generator.jl`)
  bury the "what does this do". Move history to `docs/history.md` and keep docstrings at
  about 10 lines.

## Evidence ledger

**Key claims & citations** (all from this repo or local measurement on 2026-10-13):
- Test pass count and time: local `Pkg.test()` run, "FaradayDisk | 177 177 11m38.2s".
- Sweep validation: `output/4193275_20260722_214351/logs/*.jsonl` (rmse 0.0848,
  rmse_deg 6.00); `logs/*.log` (`pass_primary = true`); `sweep/summary.csv`
  (elapsed 116.3–203.3 s).
- Allocation and time figures: `docs/audit/fused_dtn.jl` and the profiling run described
  above.
- Preconditioner result: `docs/audit/precond.jl` output.
- Dead README links: `README.md` lines 40, 51 and 58 reference sections absent from the
  file.

**Arithmetic (inference):**
- At nr=2500, n = 2·2500 + 2 = 5002.
- One LU factor is 5002² · 8 B = 200 MB; 60 factors = 12.0 GB. This matches the logged
  `ram_per_case_bytes = 12025908428`.
- One LU costs (2/3)·5002³ ≈ 8.3e10 flop.
- Per-case cost with the LU cache: 60 · 8.3e10 + 1800 steps · 2n² ≈ 5.1e12 flop.
- Per-case cost with preconditioned GMRES: 8.3e10 + 1800 · 5 iterations · 4n² ≈ 9.8e11
  flop.
- Ratio ≈ 5×.

**Assumptions / Unknowns:**
- The 3–5 iteration count was measured at nr=150 only. Behaviour at nr=2500 is
  **unverified**, and it is the main thing that would change recommendation 2.
- The nr³ extrapolation of DTN time is unverified.
- The BLAS oversubscription cost is unmeasured.
- MATLAB findings come from reading the code only.

**Risks & mitigations:**
- A preconditioner could degrade at large Γ or nr. Mitigation: if the iteration count
  exceeds about 30, fall back to the LU cache.
- Rounding-key dedup changes `g` by about 1e-12 relative. Mitigation: dedup on the exact
  symmetric phase index instead of the float value.
